# 决策记录：推理引擎由 cv2.dnn 切换为 onnxruntime

日期：2026-10-21
背景：原型在三页 PDF 实测中单页耗时 224991ms（repair 占 99.7%），超出判定预算 120s，触发 `out_of_time_budget`。

## 问题定位

- 标书主要指标第 3 条：水印去除速度 <2 分钟/张（RTX A6000 显卡运行下），为硬性门限。
- 当前推理栈 `cv2.dnn`（wm/lama.py）为纯 CPU 实现，即使部署到组委会 A6000 工作站，显卡也不会被使用，性能条款实际路径不通。
- 实测环境为组委会提供的 A6000 工作站（断网、离线部署）；本地 M1 iMac 仅作开发演示，无 GPU。

## 共识

1. **定位**：CPU 路径 = 功能正确性 + 演示可用性；GPU 路径 = 标书性能达标手段。CPU 无需独立扛住 120s 考核，但演示不可冷场。
2. **第一步（已拍板）**：引入 onnxruntime 替换 cv2.dnn。同一 ONNX 模型文件零改动、修复策略零改动（"质量一寸不让，先只换引擎"）。CPU 后端预计快 2~3 倍；预留环境变量开关切换 CUDA Execution Provider。
3. **禁止静默降级**：模型文件缺失/加载失败必须显式报错，不得悄悄回退 `cv2.inpaint`（组委会断网机上首次运行下载失败会静默倒退，本地无法复现）。约 5 行代码，并入本次改动。
4. **"缩小 LaMa 修复范围换速度"明确后置**：修整个 footprint 是撑起印章 ~95% 效果的有意设计，仅在换引擎后 CPU 仍撑不住演示时再议，且须以 fidelity/residual/印章成功率验证不回退。
5. **离线部署包内容暂缓拍板**（pip 离线包 vs Docker），归档至方案冻结前决定；不改算法代码，无返工风险。包内必含：模型文件（进 `models/`）、onnxruntime CPU+GPU 版及 CUDA 运行库、PaddleOCR 离线模型、环境自检页（报告显卡是否启用/模型是否就绪，兼作租卡验收到具）。
6. **租卡验证为必做项**：换引擎完成、软件稳定后，租 1~2 小时 GPU 实例跑同一三页文档，确认日志显示 CUDA 生效、单页 2~3s。GPU 分支在本地永远无法验证，属盲改，不测不冻结。

## 验收标准（本地可测）

| # | 条件 | 标准 |
|---|------|------|
| 1 | 速度 | 同一三页 PDF，单页 repair ≤ 120s（M1 CPU） |
| 2 | 质量 | fidelity / residual / 逐页判定与换引擎前逐项一致（输出应完全相同，仅允许毫秒级浮动） |
| 3 | GPU 开关 | 环境变量存在且代码路径正确；CUDA 实际生效留待租卡验证 |

## 复盘备注

当初为省 2GB torch 依赖选用 `cv2.dnn`，盲点是未以标书 A6000 条款压力测试该选择；onnxruntime（约 200MB）为当时遗漏的中间选项。当初选定 ONNX **格式**正确，换引擎零转换成本。

## 实施结果（2026-10-21 当日完成）

- 依赖成本为零：onnxruntime 1.31.0 已随 rapidocr 装好，本次仅显式声明。
- **质量零回退达成**：同一输入、当前代码下新旧引擎逐像素 A/B，5 种水印风格输出最大差 1/255、p99 差 0（26 万像素中仅 31 个差 1）——即渲染级一致。
- **速度实测 1.4~1.6 倍**（e2e 单页 24~36s → 14~24s），低于预估的 2~3 倍；据此外推 GUI 那页 225s 约降至 140~155s，**验收标准①（≤120s）在 M1 上未达成**。批量瓦片推理（batch）实测仅再提 ~20% 且不稳定，未采用。
- CUDA 开关 `WM_LAMA_CUDA=1` 与禁静默降级（`LamaModelMissing`）已落地；日志单行打印 providers 供现场核对。
- 结论：换引擎把"显卡从死路变正门"的目标完成；CPU 本地达标若仍需推进，进入既定后置议程（缩小 LaMa 范围等质量换速度手段，须指标验证不回退）。
